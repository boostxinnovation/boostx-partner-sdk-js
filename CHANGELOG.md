# Changelog

## v1.2.0

### Documentation
- Conforms to [boostx-partner-sdk-spec v1.2.0](https://github.com/boostxinnovation/boostx-partner-sdk-spec/tree/v1.2.0), whose version number this SDK now carries: the spec and both reference SDKs are released together under one number. Documentation only: no behaviour change
- The README says that a jackpot round sent again carries the same `round` and `boost` and keeps the `x` of the entry during which BoostX fixed its result, normally the entry that first sent it, and that `playerX` on that `x` gives the X the player saw
- The README links the spec's rules instead of the partner docs
- The README and the type documentation describe `Booster.boost` in the spec's words

## v1.1.0

### Changes
- Conforms to [boostx-partner-sdk-spec v1.1.0](https://github.com/boostxinnovation/boostx-partner-sdk-spec/tree/v1.1.0), whose GID builders refuse an id that contains `:` or exceeds its length
- `buildGID`, `createGamePassToken` and `createSettlementToken`, and so `BoostxClient.submitSettlement`, reject a `partner`, `user` or `bet` that contains `:` or is longer than 32 (`partner`), 64 (`user`) or 96 (`bet`) code points with `invalid_claim` naming the id, before signing and before anything is sent. A character outside the Basic Multilingual Plane counts as one, only `:` itself is refused, not a look-alike such as the full-width `：`, and nothing is trimmed or normalised first. Each id is checked for well-formed Unicode, then `:`, then length, before the next, and these checks still run after every other parameter check. BoostX refuses a gamepass with such an id (`401`), and the settlement builder refuses them too, so a settlement is only ever built for ids a gamepass can carry. Such an id is a fault in the calling code. Parsing an inbound token checks neither rule, so a Booster or CheckBet token whose `gid` carries such ids is still verified

## v1.0.0

### New Features
- Initial release of the BoostX partner SDK for JavaScript and TypeScript. Conforms to [boostx-partner-sdk-spec v1.0.0](https://github.com/boostxinnovation/boostx-partner-sdk-spec/tree/v1.0.0). It implements the partner side of the BoostX contract: the `/set-boost`, `/check-bet` and `/verify-keys` endpoints, the five token types with the signed GID they carry, and the settlement client. ESM with TypeScript declarations, for Node.js 22.12 or later (`require()` works through `require(esm)`, and the declarations also resolve under TypeScript's `"module": "commonjs"`), Cloudflare Workers with no compatibility flag, and other runtimes with Web Crypto and `fetch`
- Two entries: `@boostxinnovation/partner-sdk`, which uses only web-standard APIs (Web Crypto, `fetch`, `Request`/`Response` including static `Response.json` and streamed request and response bodies, `URL`, `AbortSignal.timeout`/`AbortSignal.any`, `TextEncoder`/`TextDecoder` and `atob`/`btoa`, on an ES2024 engine for `String.prototype.isWellFormed` and `toWellFormed`) and runs everywhere, and `@boostxinnovation/partner-sdk/node`, with `loadPrivateKeyFromFile`, `loadPublicKeyFromFile` and the `node:http` adapter
- Add `createFetchHandler(options)`, a `Request` → `Response` handler for the three endpoints, dispatched on the last path segment so it mounts under any prefix. A method other than `POST` is answered `405` with `Allow: POST`, an unknown path `404`, and a body over 64 KiB `400` without reading the rest, as is a body that is not strict UTF-8, starts with a byte order mark or is not a single JSON value, and one something in front of the handler already read. Every answer is JSON in the contract's `{"result": …}` / `{"error": …}` envelope, and the handler never rejects. It throws `invalid_claim` when created with options that could not serve a request: a bet store without `setBoost`, or a key store missing one of its three methods
- Add `createNodeHandler(options)` in `@boostxinnovation/partner-sdk/node`, the same handler for `node:http`, which also works as an Express route handler behind any body parser or none: it uses the body a parser read into `req.body`, and otherwise reads the request stream itself; and `handleSetBoost`, `handleCheckBet` and `handleVerifyKeys`, which take an already-parsed JSON body and resolve to `{ status, body }`, for any other framework, and answer `500` while the options they use are invalid; `handleVerifyKeys` uses no bet store, and only `boostxPublicKey` and `partnerPrivateKey` of the key store
- Add `BetStore`, with `setBoost(booster)` and an optional `checkBet(gid)`. `/set-boost` answers `{"result": {"ok": true}}` whenever `setBoost` resolves, a round sent again included; a `setBoost` that throws `RoundRejectedError`, or an error with one in its `cause` chain, is answered `400 round rejected`, never with its message, and any other error `500`. `/check-bet` is served only when the store has `checkBet`, and answers `404` otherwise; a `checkBet` that throws or resolves a non-boolean is answered `500`
- Verify the BoostX signature on every inbound token and the GID signature on every `/set-boost` and `/check-bet` call, against several partner public keys: the current one and those still valid for games started before a partner key rotation, whose GID keeps the old signature. A listed key that cannot verify, one on another curve or without the `verify` usage included, is skipped, and `500` is answered only when no listed key can verify. The keys are checked before the token, the BoostX key first, so such a configuration is answered `500` whatever the token holds. A BoostX public key or a partner private key that is not ECDSA P-256 is answered `500`, and the signing functions reject a private key on another curve with `invalid_private_key`
- Add `MemoryKeyStore`, an in-memory store keyed by partner ID that satisfies both `HandlersKeyStore` and `ClientKeyStore`: `register(partner, { partnerPublicKey, partnerPrivateKey, boostxPublicKey })`, where `partnerPublicKey` is one key or a list and any role may be left out or `null`. It rejects an empty partner ID with `missing_claim`, and a key that does not fit its role, or an empty key list, with `invalid_public_key` or `invalid_private_key`, keeping the previous registration. A lookup for an ID the store does not serve throws `unknown_partner`, which the handlers answer `400 unknown partner "<id>"`, and `/verify-keys` as `invalid verifyKeysJWT: iss-aud (unknown partner "<id>")`; any other key-store failure is answered `500`
- Add `createGamePassToken(privateKey, params)`, which stamps `iat` with the time of the call and adds no `exp`. It leaves `xMin`, `xMax` and `xDecimals` out of the token when unset, `null` or `0`, and `eventTitle` when unset, `null` or empty, sends `demo` only when `true`, and sends each lone surrogate in `eventTitle` as U+FFFD. It rejects a stake `amount` that is not a finite number of at least `0.01`, an `x` that is not above `0`, and a `currency` that is not 3 or 4 uppercase letters, with no case mapping. Missing `params` read as empty ones
- Add `createSettlementToken(privateKey, params)` with the eight statuses in `SETTLEMENT_STATUSES`, an `amount` of exactly `0` for `unsettled`, a currency of 3 or 4 uppercase letters, a `version` in `[0, 2^53−1]`, an optional `xSettle` (left out when `undefined` or `null`, sent when `0`) and a `settledAt` in milliseconds from `1e12` to 24 hours ahead. A `null` field counts as left out, and missing `params` read as empty ones
- Add `BoostxClient` with `submitSettlement(params, { signal })`, which makes a single attempt, following no redirect, and signs it, and the `gid` inside it, with the key the key store holds at that moment. It reads only the first 64 KiB of an answer and resolves only on BoostX's acceptance, `{"result": {"ok": true}}` with exact member names, in strict UTF-8 without a byte order mark; any other answer throws `BoostxAPIError`, whose `status` and `error` diagnose it (`error` is the body's `error`, `unexpected response` for a `2xx`, otherwise `HTTP <status>`), and a network failure, a timeout (30 seconds by default, `timeoutMs`, covering the key store lookup and the answer's body) or an abort propagates unchanged; a signal already aborted fails before the key store is consulted. Any failure leaves the settlement not delivered yet: send the same params again with a backoff until BoostX accepts them, as Submitting Settlements in the README describes. `baseURL` defaults to `https://partners-s2s.boostx.cloud` when unset or `null`, and takes the host or the full settlement endpoint, with or without trailing slashes and surrounding ASCII whitespace; nothing else is trimmed. The constructor throws `invalid_claim` for a `timeoutMs` that is not an integer from 1 to 2^31−1 (unset, `null` or `0` means 30 seconds), a `baseURL` that does not start with `http://` or `https://` followed by a host, an empty one included, a `fetch` that is not a function and a missing key store or one without `partnerPrivateKey`
- Add `buildGID(privateKey, partner, user, bet)`, which signs the canonical `{"partner":…,"user":…,"bet":…}` bytes exactly as `JSON.stringify` writes them, pinned against the spec's vectors, `gidgp.json` and `golden/gid-signature.json`
- Add the inbound parsers `parseBoosterToken` and `parseCheckBetToken`, with `extractBoosterPartner` and `extractCheckBetPartner` to choose the keys first. `Booster` and `CheckBet` expose the token's `iat`
- Add the verify-keys functions `createVerifyKeysRequestToken`, `parseVerifyKeysRequestToken`, `createVerifyKeysResponseToken`, `parseVerifyKeysResponseToken` and `extractVerifyKeysRequestPartner`, with `BOOSTX_IDENTITY` and a ±30-second `iat` window (`DEFAULT_VERIFY_KEYS_MAX_SKEW_SECONDS`). The parse functions resolve to `{ partnerID, nonce, iat }`. The handlers always apply 30 seconds; the parse functions take `maxSkewSeconds`, where absent, `null` or `0` means 30, a fraction is cut to whole seconds, and a negative or non-finite value throws `invalid_claim`. The nonce is an integer in `[1, 2147483647]` on both sides, judged by value, and any other nonce, of any type, is `nonce-format`; an optional `exp` or `nbf` must be a number (`shape`) and is enforced in whole seconds with no leeway (`stale`). A token with several faults gets the reason of the first failing check: format and signature, claim types, `iss`/`aud`, time, then the nonce. The `/verify-keys` response is signed as the partner ID the key store returned keys for, never for an ID it does not serve, and the partner ID `boostx` is rejected; the creators also reject one containing a lone surrogate, after the nonce. The request creator and the response parser are test aids that apply the SDK's own rules, never more lenient than BoostX's
- Add `playerX(xBase, boost, decimals)`, the X the player saw for a Booster token's `boost`, which floors `xBase` first, as BoostX floors `xrange.init` on receipt; and `floorX(x, decimals)`, the flooring step alone, by BoostX's rule. Both are pinned against the spec's golden vectors, `golden/floor-x.json` and `golden/player-x.json`
- Add `loadPrivateKeyFromPEM` (PKCS#8, or SEC1 including `openssl ecparam -genkey` output, which must name the P-256 curve in its parameters; in either format an embedded public key is optional and, when present, must be the uncompressed point of the private key; the body must be exactly the key's structure, with no bytes after it, checked by the SDK so that every runtime gives the same answer) and `loadPublicKeyFromPEM` (SPKI with an uncompressed point), from a string or bytes; any other input throws the key error. A key is the first block whose `BEGIN` line carries one of the role's labels, up to its `END` line, wherever it sits in the text; a literal `\n` or `\r\n` is read as a line break, as environment variables often carry it, and only spaces, tabs, line breaks, vertical tabs and form feeds are removed from the body, which must be padded base64. A failure names its cause: an encrypted key, which is not supported, a PEM block of another type, no PEM block, a block without its `END` line, a body that is not base64, a `PRIVATE KEY` body that is not PKCS#8 for P-256 (the label decides the format), a malformed SEC1 key, a SEC1 key that does not name P-256, an embedded public key that is compressed or does not match the private key, or a compressed point. Keys are Web Crypto `CryptoKey`s on P-256
- Add `BoostxError`, with a `code`, a `cause` chain from each parser to the lower-level failure, and `reason` on a verify-keys failure; `isBoostxError(err, code)`, which walks the chain like Go's `errors.Is`; and `verifyKeysReason(err)`, which maps a verify-keys failure to its wire reason, and a public key that cannot verify to `signature`
- Check the private key before any other argument in every signing function. Reject an empty `partner`, `user` or `bet` with `missing_claim`, a non-string one with `invalid_claim`, and an identifier containing a lone surrogate with `invalid_claim` before signing, and refuse a Booster or CheckBet token that lacks `iat` or carries a claim of the wrong type or out of range. A Booster or CheckBet token's `exp` and `nbf` are optional, as BoostX sends neither, and enforced when present, in whole seconds with no leeway: an `exp` that is not a number or not after now, or an `nbf` that is not a number or after now, is `invalid_claim`
- Refuse as malformed an inbound token whose header or payload segment is not canonical base64url, or whose header or payload is not strict UTF-8, starts with a byte order mark, is not a single JSON object or holds an unpaired surrogate escape (`\uD800` to `\uDFFF`). Read only `alg` and `crit` from the header, ignoring every other member: an `alg` other than `ES256`, any `crit`, or a signature segment that is not 64 bytes of canonical base64url is a signature failure. A GID signature that is not 64 bytes of canonical base64url fails before any key is tried, as `invalid_signature` with `invalid_gid` in its `cause` chain, like one no listed key verifies
